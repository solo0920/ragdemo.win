# Feature Specification: moj-format-ingest-audit

**Feature Branch**: `002-moj-format-ingest-audit`

**Created**: 2026-10-05

**Status**: Draft

**Input**: User description: "依司法院網站格式制定ingest資料清洗規則，然後檢查parquet, postgres, qdrant的ingest過程是否有照司法院的格式來作存入，應在回答時和司法院一致"

## 問題陳述（實測，非推測）

2026-10-05 使用者拿司法院證券交易法頁面與本專案回答比對，發現**項次消失**。
隨後完成五層全量稽核（司法院 HTML／Open API／parquet／PostgreSQL／Qdrant，
證券交易法 229 條），結果如下：

| 層 | 內容逐字一致 | 段數一致 | 備註 |
|---|---|---|---|
| 司法院 HTML | ✓ 0 條不符 | ✓ 0 條不符 | 即時抓取，229 條 |
| Open API（`/api/ch/law/json`） | 基準 | ✓ 0 條不符 | 本地 `ChLaw.json` sha 與 `.law_sync.json` 相符 |
| parquet | ✓ 0 條不符 | ✓ 0 條不符 | 229 條 |
| PostgreSQL | ✓ 0 條不符 | ✓ 0 條不符 | 229 條 |
| **Qdrant** | **20 條缺漏** | ✓ | **僅 209 條** |

### 發現 1：項次消失是呈現層問題，資料層無誤

五層的第14條都是 7 段／行（HTML 7 個 `line-*` div、API 7 行、parquet 7、pg 7、
qdrant 7）。根因在回答層把 `\n` 壓成空格 —— 而換行是**結構資訊**：
結構解析靠它計算「項／款」數量，壓掉等於資訊遺失。

### 發現 2：Qdrant 少 20 條是排除廢止條文所致

缺少的第9／17／28／52／73／76／77／78／80／101／106／131／146／155／
174-2／176／180／182 條，內容全為「（刪除）」。舊設計刻意排除廢止條文。

但**排除是錯的處理方式**：使用者問「第9條」時，正確答案是「第9條已刪除」，
不是「查不到」。查不到會被誤讀成系統未收錄或條號有誤，且沒有任何徵兆。

### 發現 3：「top5 應為 14-1～14-6」是錯誤的預期

第14條的 6 個項不是獨立法條；「第14-1條」至「第14-6條」是**插入條**
（內部控制制度、獨立董事、審計委員會、薪資報酬委員會），內容與第14條主題不同。
條以單一資料點儲存（`article_seq=15`）是正確粒度；拆成項級會讓一個問題
召回 5 筆與答案無關的內容。

### 發現 4：司法院 HTML 的分段規則與 Open API 一致

HTML 的 `line-NNNN` class **不是項序號**：`line-0000` 是項、`line-0004` 是**款**，
部分項帶 `show-number`（頁面不印項次）。實測第14條 7 vs 7、第15條 4 vs 4，
兩者分段規則相同。官方 HTML 的 `<div class="line-*">` 是可靠的條文邊界。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 回答與司法院原文一致 (Priority: P1)

使用者查「證券交易法第14條」，得到的條文內容與段落切分，與司法院網站逐項對照後一致：
項與項分隔可辨、款次標籤（「一、」「（一）」）不消失、可逐字核實。

**Why this priority**: 這是使用者當初發現問題的切入點。若回答與官方原文不一致，
整個 RAG 的可信度（constitution VI）在法律合規情境下不成立 —— 其他需求都建立在它之上。

**Independent Test**: 取任一含多項／多款之法條，輸入條號查詢，
將回答文字與司法院頁面並排比對，段落數與每段開頭字元一致。

**Acceptance Scenarios**:

1. **Given** 一部含多項的條文（例：證券交易法第14條，共6 項）
   **When** 使用者以「法名＋條號」查詢
   **Then** 回答逐字引用該條原文，各項分隔保留，不被合併為單段
2. **Given** 一條含多款（款次標籤為「一、二、三」）的條文
   **When** 回答顯示該條
   **Then** 每個款次標籤都完整出現，不被截斷或吞掉
3. **Given** 該條有已被刪除的項（原文為「（刪除）」）
   **When** 回答顯示
   **Then** 顯示「（刪除）」而非空白，且該筆被標示為已廢除

---

### User Story 2 - 廢止條文查得到、且明確標示 (Priority: P2)

使用者查「證券交易法第9條」（該條已刪除），得到「第9條已刪除，無現行條文可引用」，
而不是查不到。使用者在引用清單中看到的已刪除條文帶有明確標記。

**Why this priority**: 稽核發現 qdrant 少了 20 條全是「（刪除）」，且查不到時
沒有任何徵兆。使用者無法區分「這條已刪除」與「系統沒收錄」。這在法律情境下
會導向錯誤的判斷。

**Independent Test**: 查一條已刪除條文的條號，答案說明其已廢止；
引用清單中該筆帶廢止標記。

**Acceptance Scenarios**:

1. **Given** 一條已刪除的條文
   **When** 使用者以條號查詢
   **Then** 回答說明該條已刪除、無現行條文，而非無結果
2. **Given** 引用清單中含已刪除條文
   **When** 檢視引用
   **Then** 該筆帶有「已刪除」標記，且與現行條文的呈現明顯不同
3. **Given** 某一條全部的可用引用都已廢止
   **When** 系統判斷信心
   **Then** 信心 MUST NOT 為最高等級

---

### User Story 3 - 三段儲存層內容一致 (Priority: P3)

維運者能確認 parquet、PostgreSQL、Qdrant 三個儲存層保存的條文**數量與內容**
完全相同 —— 沒有任何一層少了條文，沒有任何一層私自改寫或排除內容。

**Why this priority**: 三層不一致時，故障會表現為「某台機器回答不同」——
這在本專案是已發生過的模式（三機資料版本不同步）。2026-10-05 稽核已實測
發現 Qdrant 少 20 條，證明這個缺口真實存在。

**Independent Test**: 對同一批條文，比對三層的條數與正文。

**Acceptance Scenarios**:

1. **Given** 同一批條文已寫入三層
   **When** 逐層取出比對
   **Then** 三層的條文**數量相同**且內容逐字相同
2. **Given** 某一層的條數少於其他層
   **When** 執行格式檢查
   **Then** 該層被明確標示為不符，並列出缺少的條號

---

### Edge Cases

- **已廢止／已刪除條文**：「（刪除）」與廢止旗標必須保留，不可當成空內容處理。
- **極長條文**：單一條文內容量超過切塊上限時，塊之間不可切在某個項的中間；
  且引用必須能指出完整原文而非其中一塊。
- **含縮排全形空白的原文**：司法院部分條文以全形 ideographic space（　）縮排項次，
  清洗不可移除該語意，但顯示時不可讓讀者誤判為新的段落邊界。
- **款次標籤與項次同時存在**：「一、」是款、「第X項」是項，兩者不可互相覆蓋或推論。
- **上游來源不可用**：司法院服務中斷時，系統應保留既有資料並明確回報「未更新」，
  不可讓查詢變成無資料狀態。
- **三台資料版本不一致**：任一機器回答與官方不符時，應可判定是資料版本問題或清洗問題，
  而不是只在該台修正。

## Requirements *(mandatory)*

### 引用格式基準

- **FR-001**: 系統 MUST 以司法院全國法規資料庫的呈現格式作為條文內容的唯一格式基準。
- **FR-002**: 清洗規則 MUST 保留條文的項次分隔，不得將多項合併為單一段落。
- **FR-003**: 清洗規則 MUST 保留款次標籤（「一、」「（一）」「1.」）及其順序。
- **FR-004**: 清洗規則 MUST 保留「（刪除）」等原地標記，不得轉為空字串。
- **FR-005**: 清洗規則 MUST 保留已廢止／已中止標記，供檢索端判斷。
- **FR-006**: 清洗規則 MUST 對條號保留原始編號格式，包含「第14-1條」這類帶橫線的編號。
- **FR-007**: 系統 MUST 提供一份可執行的格式檢查，驗證任一条文是否符合基準格式。

### 三段儲存層一致性（**最高標準**）

- **FR-008**: parquet、PostgreSQL、Qdrant 三層保存的條文**集合與正文** MUST 逐字相同。
  一層少一條即為不符 —— 沒有「因為它不重要所以可以少」的例外。
- **FR-009**: 清洗規則 MUST 僅在資料進入儲存前施加一次；三層之間 MUST NOT 各自再清洗。
- **FR-010**: 超長條文的切塊 MUST 不切在某個項的中間，且每塊 MUST 可還原為完整原文。
- **FR-011**: 系統 MUST 讓引用顯示的內容可追溯到完整原文，而非僅某個切塊。
- **FR-021**: 儲存層 MUST 保留已廢止／已中止條文，並保留其原始標記
  （例：「（刪除）」）與狀態旗標。
- **FR-022**: 狀態旗標 MUST 存放**真實值**，MUST NOT 以常數代替 ——
  常數會讓下游的篩選失效，且使該層與其他層不一致。
- **FR-023**: 排除任何資料的決定 MUST 由**查詢時**的判斷達成，MUST NOT 在**存入時**達成 ——
  存入時排除會讓資料永久不可見且不可稽核。

### 廢止條文的呈現

- **FR-024**: 系統 MUST NOT 以「查不到」回應一個已廢止條文的條號查詢 ——
  正確回應是說明該條已廢止。
- **FR-025**: 引用清單 MUST 明確標示已廢止／已中止條文，且 MUST NOT 讓其
  與現行條文同等呈現。
- **FR-026**: 當可用引用全為廢止條文時，信心分級 MUST NOT 給出最高等級。

### 檢索與引用粒度

- **FR-012**: 條文 MUST 以「一條一點」為儲存與檢索粒度；MUST NOT 拆成多個
  資料點 —— 插入條（第14-1條等）是獨立法條，與該條的項是不同對象。
- **FR-013**: 引用標示 MUST 能區分條、項、款三個層級。
- **FR-014**: 引用 MUST NOT 包含條號與查詢意圖無關的條文而無任何說明。

### 回答與官方一致

- **FR-015**: 以條號精準命中時，回答 MUST 逐字引用該條原文，MUST NOT 由模型改寫。
- **FR-016**: 回答中的條文內容 MUST 保留項次分隔，使讀者能逐項對照官方原文。
- **FR-017**: 回答 MUST 能標示引用來自哪一條的哪一項。

### 可追溯與失敗可分辨

- **FR-018**: 每次回答 MUST 能追溯到來源法規、條號、項／款位置與使用的檢索機制。
- **FR-019**: 資料未更新（上游不可用）與資料格式錯誤 MUST 表現為可區分的兩種狀態。
- **FR-020**: 格式檢查失敗時 MUST 指出是哪一條、哪一層、差在哪裡，
  而非僅回報「有資料不符」。

### Key Entities

- **法律條文（Article）**：法規中的一條。可含多個項；本身是檢索與引用的最小完整單位。
- **項（Paragraph）**：條文內的編號段落（司法院以「第X項」或前段引用指稱）。
- **款（Sub-paragraph）**：項內以「一、」「（一）」標示的細目。
- **清洗規則（Cleaning Rule）**：把上游原始回應轉為基準格式的規則集；
  於進入儲存前施加一次。
- **儲存層（Store）**：parquet（備份／分析）、PostgreSQL（關聯查詢）、
  Qdrant（向量檢索）。三者保存同一份清洗後內容。
- **格式檢查（Conformance Check）**：驗證某條文／某儲存層是否符合基準格式的檢查。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 對任一含多項的法條，系統回答的段落數與司法院原文**完全相同**
  （以 10 部法、每部 5 條為抽樣，100% 相符）。
- **SC-002**: 抽樣 100 條含款次標籤的條文，款次標籤在回答中**100% 完整保留**。
- **SC-003**: 以條號查詢時，該條本身 MUST 是引用清單的**第一筆**。
- **SC-004**: 三層儲存的條文**數量與正文**完全相同，差異數為 **0**
  （2026-10-05 基線：證券交易法三層皆為 229 條，內容逐字一致）。
- **SC-005**: 使用者對照司法院原文提出的格式不符回報，修正後**重複發生率為 0**
  （以連續 20 次查詢計）。
- **SC-006**: 格式檢查能於單次執行內辨識出注入的格式錯誤，並指出**是哪一條、哪一層**。
- **SC-007**: 條號查詢的回應時間維持在**與修正前相當**（增幅不超過 20%）。

## Assumptions

- **以司法院 API／網站為格式基準**：上游資料來源維持現有來源；
  本功能不更換來源，只規定進入儲存前的清洗規則。
- **既有資料可重新產生**：parquet 與儲存層內容可由上游重新導出重建，
  不需人工修補。重建前需保留可回退的備份。
- **條號帶橫線的條文（例第14-1條）確實存在於來源**：實測司法院證券交易法頁面
  列有「第 14-1 條」至「第 14-6 條」，故資料層需能表示它們。
- **項級切分不改變法律效力**：切分只是儲存與檢索的粒度，回答仍以完整條文為準。
- **不追求完全等同官方 HTML 版面**：本功能針對**條文內容與結構**一致，
  不包含官方頁面的版面、字級、導覽列等呈現。
- **既有詞庫、規則卡與題庫機制不變**：本功能只規範條文的清洗與儲存格式，
  不改變規則題庫比對或 JEV 驗證流程。
